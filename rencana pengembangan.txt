# 1. Pendahuluan

## 1.1 Latar Belakang

Teras Kota merupakan aplikasi POS berbasis web Laravel yang telah memiliki karakteristik PWA. Target pengembangan adalah membuat fungsi POS tetap dapat digunakan pada smartphone ketika koneksi internet tidak tersedia, kemudian melakukan sinkronisasi transaksi ke server saat koneksi kembali tersedia.

Pendekatan yang digunakan adalah **offline-first**: server Laravel + database tetap menjadi sumber data pusat, sedangkan smartphone memiliki penyimpanan lokal menggunakan **IndexedDB** untuk app shell, master produk yang diperlukan POS, transaksi offline, dan antrean sinkronisasi.

## 1.2 Definisi

| Istilah | Definisi |
|---|---|
| PWA | Progressive Web App; aplikasi web yang dapat dipasang dan memiliki kemampuan app-like. |
| Offline-first | Aplikasi tetap menjalankan fungsi inti tanpa bergantung pada koneksi jaringan. |
| IndexedDB | Database browser lokal untuk menyimpan data terstruktur. |
| Sync queue | Antrean transaksi lokal yang belum berhasil dikirim ke server. |
| `sync_id` | UUID unik global untuk menjamin idempotency transaksi. |
| Idempotency | Pemrosesan request berulang menghasilkan efek bisnis satu kali. |
| App shell | HTML/CSS/JS/resource minimum agar POS dapat dibuka offline. |
| Conflict | Kondisi ketika keadaan lokal dan server tidak dapat digabungkan tanpa keputusan bisnis. |

# 2. Kondisi Sistem Saat Ini

## 2.1 Teknologi

| Komponen | Kondisi Baseline | Implikasi Offline |
|---|---|---|
| Backend | Laravel/PHP | Tetap menjadi server transaksi dan sumber kebenaran. |
| Database | Database server | Tidak tersedia ketika smartphone offline. |
| Frontend | Blade + JavaScript + Bootstrap/CDN | Resource CDN perlu dilokalkan/dicache. |
| Build | Vite | Dapat digunakan untuk bundling asset lokal. |
| PWA | manifest + `public/service-worker.js` | Service worker belum menyediakan POS app shell penuh. |
| POS checkout | POST ke route `pos.checkout` | Tidak dapat membuat transaksi ketika server tidak terjangkau. |
| Transaksi | `TransactionService` + DB transaction | Logic server perlu dipakai kembali oleh endpoint sync. |

## 2.2 Titik Kode yang Menjadi Baseline

| File | Peran | Perubahan Target |
|---|---|---|
| `app/Http/Controllers/PosController.php` | Index, checkout, receipt, summary | Tambah flow sync/data offline. |
| `app/Services/TransactionService.php` | Pembuatan transaksi dan detail | Tambahkan idempotency dan pemrosesan sync. |
| `app/Models/Transaction.php` | Model transaksi | Tambah metadata sync. |
| `database/migrations/*transactions*` | Schema transaksi | Tambah UUID/idempotency dan metadata sync. |
| `routes/web.php` | Route POS | Tambah route sync/bootstrap. |
| `resources/views/pos/index.blade.php` | UI + logic POS | Pisahkan logic JS dan local-first checkout. |
| `resources/views/layouts/pos.blade.php` | Shell POS | Kurangi ketergantungan CDN. |
| `public/service-worker.js` | Service worker | Cache app shell POS dan strategi offline. |
| `public/manifest.webmanifest` | Manifest PWA | Pastikan scope/start URL sesuai POS. |
| `resources/js/app.js` | Entry frontend | Integrasi modul offline jika diperlukan. |
| `vite.config.js` | Bundling | Pastikan asset offline dibuild. |
| `package.json` | Dependency/build | Tambah dependency hanya bila diperlukan. |

## 2.3 Keterbatasan Baseline

- Service worker saat ini hanya memiliki fallback ke `offline.html` untuk navigasi yang gagal; halaman POS belum menjadi app shell offline.
- Checkout POS bergantung pada request ke Laravel.
- Belum ada IndexedDB untuk transaksi POS.
- Belum ada sync queue dan endpoint sinkronisasi khusus.
- Nomor transaksi saat ini dibuat server-side dari transaksi terakhir pada tanggal tersebut; mekanisme tersebut tidak cocok sebagai identifier offline.
- Summary hari ini mengambil data dari server.
- Receipt saat ini dapat dirender server-side; mode offline memerlukan renderer lokal.
- Asset UI dari CDN harus tersedia lokal/cache.
- Autentikasi offline memerlukan kebijakan eksplisit; password server tidak boleh disimpan plaintext.

# 3. Tujuan dan Sasaran Pengembangan

## 3.1 Tujuan Utama

1. Kasir dapat membuka POS pada smartphone tanpa koneksi internet setelah perangkat dipersiapkan saat online.
2. Kasir dapat melihat master menu yang telah disinkronkan.
3. Kasir dapat membuat transaksi penjualan offline.
4. Transaksi offline tersimpan durable di IndexedDB.
5. Transaksi otomatis/manual dapat disinkronkan saat koneksi kembali.
6. Server mencegah transaksi offline yang sama tersimpan lebih dari satu kali.
7. Receipt dapat ditampilkan/cetak tanpa bergantung pada server.
8. Status offline, pending sync, synced, failed, dan conflict dapat diketahui kasir.
9. Sistem tetap kompatibel dengan checkout online yang berjalan saat ini.

## 3.2 Target Operasional

| Target | Kriteria |
|---|---|
| Transaksi offline | Minimal transaksi tunai dapat selesai tanpa internet. |
| Durability | Transaksi lokal tetap ada setelah refresh/close-reopen. |
| Sync | Antrean dikirim kembali ketika koneksi tersedia. |
| Idempotency | Retry request tidak membuat transaksi ganda. |
| Recovery | Kegagalan sync tidak menghapus transaksi lokal. |
| UI | Kasir mengetahui status koneksi dan sinkronisasi. |

# 8. Rancangan Data dan Sinkronisasi

## 8.1 IndexedDB Stores

| Store | Key | Isi |
|---|---|---|
| `metadata` | `key` | schema version, last master sync, device_id, user_id, app_version |
| `categories` | `id` | Kategori aktif |
| `menus` | `id` | Menu aktif: name, category, price, profit policy, updated_at |
| `transactions` | `local_id` | Snapshot transaksi, payment, status, timestamp |
| `sync_queue` | `local_id` | Retry state, attempt count, error, next attempt |

## 8.2 Server Schema Tambahan

| Field | Tipe | Tujuan |
|---|---|---|
| `sync_id` | UUID UNIQUE | Idempotency key transaksi |
| `source_device_id` | string nullable | Identitas perangkat sumber |
| `sync_status` | enum/string | Status sync server bila diperlukan |
| `synced_at` | timestamp nullable | Waktu server memproses sync |

Penambahan field dilakukan melalui migration baru. Migration historis tidak diedit pada database produksi.

## 8.3 State Machine

```text
LOCAL_DRAFT → PENDING_SYNC → SYNCING → SYNCED
                         ├→ FAILED_RETRYABLE → PENDING_SYNC
                         └→ CONFLICT / FAILED_FINAL
```

| Status | Makna | Aksi |
|---|---|---|
| `draft` | Belum checkout | Dapat diedit/hapus |
| `pending_sync` | Sudah checkout, belum server | Jangan hapus |
| `syncing` | Sedang dikirim | Hindari pengiriman paralel |
| `synced` | Server mengakui transaksi | Simpan server ID/number |
| `failed_retryable` | Gagal sementara | Retry |
| `conflict` | Butuh keputusan bisnis | Jangan retry otomatis tanpa aturan |

## 8.4 Algoritma Sync

1. Ambil transaksi `pending_sync`/`failed_retryable` yang waktunya sudah jatuh tempo.
2. Ubah status lokal menjadi `syncing`.
3. Kirim payload dengan `sync_id` dan `device_id`.
4. Server mencari `sync_id`.
5. Jika sudah ada dan sukses, server mengembalikan transaksi existing.
6. Jika belum ada, server memvalidasi payload.
7. Server memanggil `TransactionService` dalam DB transaction.
8. Server mengembalikan `server_id`, `transaction_number`, status, dan data receipt.
9. Client mengubah status menjadi `synced`.
10. Item queue dihapus hanya setelah server mengakui sukses.
11. Error jaringan menjadi `failed_retryable`.
12. Conflict bisnis menjadi `conflict`.

# 9. Rancangan API

## 9.1 Bootstrap

| Method | Endpoint | Tujuan |
|---|---|---|
| GET | `/api/pos/bootstrap` | Mengambil master data POS |
| GET | `/api/pos/summary-today` | Summary server hari berjalan |

## 9.2 Sync

```http
POST /api/pos/sync
```

### Payload

```json
{
  "sync_id": "UUID",
  "device_id": "DEVICE-UUID",
  "transaction_date": "YYYY-MM-DD",
  "transaction_time": "HH:MM:SS",
  "payment_method": "tunai",
  "cash_tendered": 50000,
  "customer_name": null,
  "notes": null,
  "items": [
    {
      "menu_id": 10,
      "quantity": 2
    }
  ]
}
```

### Response

```json
{
  "success": true,
  "status": "synced",
  "sync_id": "UUID",
  "server_id": 123,
  "transaction_number": "TRX-YYYYMMDD-XXXX"
}
```

> Total transaksi dari client tidak boleh dianggap sebagai source of truth. Server menghitung ulang berdasarkan master data dan business rule.

# 10. Rancangan Service Worker dan PWA

| Resource | Strategi |
|---|---|
| POS app shell | Cache-first / precache |
| CSS/JS/fonts/icons | Precache/cache-first |
| Master API | Network-first + IndexedDB fallback |
| Transaction POST | Dikelola aplikasi POS + IndexedDB queue |
| Non-POS navigation | Fallback `offline.html` |

Service Worker harus:

- menggunakan cache versioning;
- menangani cache lama;
- tidak menghapus IndexedDB;
- memiliki icon yang benar-benar tersedia;
- memastikan manifest, scope, dan start URL sesuai;
- tidak bergantung pada CDN untuk fungsi inti POS.

# 12. Keamanan

- Gunakan HTTPS.
- Jangan menyimpan password user di IndexedDB/localStorage.
- Gunakan `device_id` acak/UUID.
- Batasi endpoint sync berdasarkan user/device.
- Gunakan CSRF/token sesuai mekanisme autentikasi.
- Server selalu memvalidasi `menu_id` dan policy harga.
- Server menghitung ulang total.
- Jangan percaya `total_sales`/`total_profit` dari client.
- Simpan data lokal minimum.
- Sediakan revoke device.
- Jangan memasukkan secret ke JavaScript bundle.

# 13. Penanganan Konflik dan Kegagalan

| Kasus | Respons |
|---|---|
| Internet putus saat checkout | Simpan transaksi lokal |
| API 500 | Retry dengan backoff |
| Response hilang setelah commit | Retry dengan `sync_id`; server mengembalikan transaksi existing |
| Menu sudah tidak ada | Conflict/final failure |
| Harga berubah | Terapkan business rule yang ditetapkan |
| Stok tidak cukup | Conflict |
| Dua device menjual stok sama | Server menjadi authority |
| Storage browser dihapus | Data lokal yang belum sync dapat hilang; sistem harus memperingatkan |

1. Setelah bootstrap online, POS dapat dibuka dan menampilkan master menu tanpa koneksi.
2. Kasir dapat menyelesaikan transaksi tunai offline.
3. Transaksi offline tetap ada setelah PWA ditutup/dibuka.
4. Setiap transaksi memiliki `sync_id` unik.
5. Ketika internet kembali, transaksi dikirim tanpa input ulang.
6. Retry tidak menghasilkan transaksi ganda.
7. Nomor transaksi server tersedia setelah sync.
8. Receipt dapat ditampilkan/cetak offline.
9. UI menampilkan status offline dan pending sync.
10. Error sync tidak menghapus transaksi lokal.
11. TC-01 sampai TC-15 lulus pada perangkat target.

# 17. Risiko dan Mitigasi

| Risiko | Dampak | Mitigasi |
|---|---|---|
| Storage browser dihapus | Transaksi belum sync hilang | Auto-sync + indikator pending + peringatan |
| Multi-device stock conflict | Stok tidak konsisten | Server authority + conflict policy |
| CDN tidak tersedia | UI rusak | Bundle/cache dependency lokal |
| Duplicate sync | Double transaction | `sync_id UNIQUE` + idempotent endpoint |
| Harga berubah | Nilai berbeda | Business rule + server validation |
| Session expired | Tidak dapat sync | Device authorization |
| Service worker stale | Bug versi lama | Cache versioning |
| Clock perangkat salah | Timestamp lokal salah | Server timestamp sebagai waktu penerimaan |

| Identifier offline | UUID `sync_id` |
| Nomor nota | Ditetapkan server |
| Stok | Server authority; conflict jika tidak cukup |
| Authentication | Device harus pernah online dan terotorisasi |
| Receipt | Renderer lokal |
| Sync | Otomatis + manual |
| Retry | Exponential backoff |
| Master data | Sync online + `updated_at`/version |
